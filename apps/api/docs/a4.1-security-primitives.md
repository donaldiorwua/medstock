# A4.1 — Security primitives

This milestone adds reusable cryptographic primitives only. It does not implement login,
logout, database session creation, cookies, middleware, CSRF enforcement, lockout, rate
limiting, or audit writing. Those belong to later A4 slices.

## Passwords

Use `hash_password(password)` when creating or changing a password. It uses Argon2id with
explicit parameters: 19 MiB memory, two iterations, one lane, a 32-byte output and a
16-byte random salt. The API's existing `Password` schema enforces 10–128 characters.
Passwords are not stripped or otherwise normalised; whitespace is significant.

Use `verify_password(plain_text, encoded_hash)` to verify a login or current password. It
returns `False` for a mismatch or malformed hash. Use `password_needs_rehash(encoded_hash)`
after successful verification to identify hashes that should be upgraded to the current
profile. Do not log passwords or encoded password hashes.

## Session bearer tokens

Call `generate_session_token()` to create the random bearer token delivered to the client.
Call `hash_token(token)` before persisting it in `UserSession.token_hash`. The stored value
is a 64-character lowercase SHA-256 hex digest, matching the existing `String(64)` column.
Never persist or log the raw bearer token. When a token is presented, verify it against the
stored digest with `verify_token(token, stored_hash)`.

The future login endpoint must send the raw token only in the `medstock_session` cookie.
That cookie should be HttpOnly, Secure in staging/production, and use an intentional
SameSite policy. Session expiry and revocation remain database responsibilities.

## CSRF tokens

Call `generate_csrf_token(raw_session_token)` after authenticating the session. The token
is a deterministic HMAC-SHA256 derivation using the high-entropy session token as its key
and a fixed, versioned application context. This avoids storing an additional CSRF secret
in the existing session table. Return it from the existing `GET /auth/csrf` endpoint and
require the client to echo it in `X-CSRF-Token` on state-changing requests.

Validate it with `verify_csrf_token(raw_session_token, supplied_token)`. A CSRF token from
one session does not validate for another session. CSRF protection does not replace XSS
prevention; scripts running in the trusted origin may be able to read the CSRF response.

## Dependency management

`argon2-cffi` is declared in `requirements.in`; `requirements.txt` contains pinned versions
for it and its transitive dependencies. When changing dependency constraints, regenerate
the lock with the project's normal pip-tools workflow rather than editing pins by hand:

```bash
pip-compile --output-file=requirements.txt requirements.in
```

## Verification

Run the focused tests first, then the full suite:

```bash
pytest -q tests/test_security_primitives.py
pytest -q
```

The security primitive functions are deliberately independent of FastAPI and SQLAlchemy.
Later milestones should compose them in services and dependencies rather than duplicate
cryptographic logic in endpoint handlers.
